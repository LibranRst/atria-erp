# AI Agent Architecture

[Role/permission Browser verification](../guide/ai-role-permission-verification-2026-10-13.md) covers scoped project reads, stock/finance separation, own proof and revocation using actual sessions. Global project/bank access remains within INSTANCE_TENANT_ID; metadata/stock references and aggregates enforce the same boundary. The shared money DTO retains sen. Company-wide bank aggregates carry authoritative count/total, while paged references disclose their actual filter. /ai resolves the Actor and refuses denied access before mounting chat controls; the restricted state reuses existing PageState/ButtonLink and top-bar clearance.

Current backend ownership: `apps/api/src/backend`; Next actions are typed HTTP facades. The capability catalog filters tools by effective DB permissions and project scope. See [action coverage](AI_ACTION_COVERAGE.md) for supported proposals and module gaps. Expense examples below illustrate the two-phase contract rather than enumerating all available writes.

[Live model acceptance](../guide/ai-live-conversation-verification-2026-10-13.md) records Browser messages, model-selected tools and persisted confirmations for sampled flows. Prior lookup/proposal quantities are historical snapshots; stock tools re-read current data and return authorized bounds on failed reductions. Completed setup omits machine step IDs. Regular-project input requests share the final capability gate; context distinguishes missing grants from unimplemented workflows.

## Contextual proposal confirmation

`features/ai-chat/utils/proposal-review-flow.ts` deterministically chooses the presentation for catalog settings, project stock, procurement/warehouse, RAP setup/lifecycle/saved changes, category packages and saved RAB workflow from validated actions, changed fields, affected rows, source links and budget impact. The model cannot choose or bypass this policy. Small single-record changes show complete differences and an explicit action directly in the chat card. Sensitive bank, valuation, physical-stock, deletion, finalization and financial-approval decisions add one short shared `ConfirmationDialog`. Multiple changed rows, large patches, full templates, baseline revisions, budget risk and editable/selection/import drafts retain a dedicated `FormSheet`; only sensitive actions add a dialog.

`ProposalInlineReview` composes existing `ProposalDiffRow`, `FactRow`, fullDynamic `MoneyValue`, `FormDisclosure` and feature row renderers. Mandatory reasons, quantities, sources and permitted financial consequences remain visible before approval. Secondary context expands on the card; embedded recovery feedback retains its action without another elevated surface. Presentation width does not change the review policy. Server-owned proof, live grants/scope, context freshness, atomic writers, maker/checker, audit and idempotent receipts remain unchanged. Existing Material Master and legacy finance/role paths preserve their established behavior.

## RAP Material draft proposals

`getRapDraftContext` reads scoped project candidates, the latest Draft RAP, Material budget usage, active materials, verified reference prices and owned review drafts including applied corrections. It reads those corrections without initializing or changing a draft. Historical assistant text can predate user edits, so the model reads current review context before continuing a proposal. `proposeRapMaterialDraft` produces 1–50 conversation rows as an immutable owned assistant source. Units and material identities come from Material Master; missing prices require user input.

`getAiRapDraftProposal` initializes an owned RAP `form_draft` from that source through an ordinary fixed operation. The payload stores only permitted row corrections, with immutable material/row IDs and budget/reference context retained in the assistant proof. `patchAiRapDraftProposal` checks Actor grants/assignment, ownership, 30-day source expiry, live context and expected revision, then recalculates exact quantities, cost and stock hints and persists the corrections. It changes no business RAP, inventory, cash or budget usage. The draft retains the source expiry; applying corrections does not silently extend it.

`confirmAiRapDraftProposal` accepts conversation/tool identity and reviewed revision; legacy identity-only saves remain valid for untouched revision 1. It rechecks the current business context, creates/appends through shared transactional writers, and consumes the review draft atomically with RAP items, audits and the existing idempotent confirmation receipt. Consumed corrections remain available for historical confirmed review. Replaying confirmation returns the original material row IDs. Editing a consumed proposal is rejected; changed business context requires a new proposal.

The compact chat card shows the project, proposed estimate, row count and planned budget condition. Review uses one stable FormSheet: desktop table plus a side summary/action panel, mobile grouped rows with an inline editor. Area, quantity, buffer and unit estimate can be edited; identities and units remain fixed. Exact local preview updates immediately, Apply persists corrections, and business Save remains disabled while unapplied changes exist. Apply retains its target after success to prevent a rapid second click from becoming Save. Pagination is five/ten rows, focused inputs remain mounted across resize, and applied corrections restore after reload. Shared DesktopTable and BottomSheet gained opt-in responsive review/aside-footer presentation; other consumers retain their defaults.

## Capability answers and Material Master editing

getAvailableActions returns permission/scope-filtered read and proposal groups plus a bounded list of manual gaps from the same capability catalogue. Prompt and explainUserAccess distinguish ERP authorization from implemented AI actions; Owner rights do not imply every workflow exists in chat.

getEditableMaterials includes inactive materials, bounded search results/disambiguation and existing category/vendor IDs. proposeUpdateMaterial reads the current material and returns metadata/status before/after with its version; it writes nothing. The card loads the owned, stored assistant output through getAiMaterialUpdateProposal. Confirmation accepts only conversation/tool identity, reloads that proposal, rechecks fresh Actor permissions and its 30-day lifetime, and rejects changed material versions or invalid references.

Settings updateMaterial, setMaterialActive and archiveMaterial share transactional master-editor writers with the AI path. Tenant catalog and material locks serialize duplicate identity checks against active/inactive records; versions advance monotonically. The material write, audit and AI confirmation receipt share one commit. Replay does not repeat the update. Inventory balances/defaults/cost, stock movements and cash transactions are outside this metadata/status operation. Conversational corrections create another reviewed proposal; they never execute writes.

## Material Master import

Text input and XLS/XLSX/CSV/image/PDF attachments produce an owned `MATERIAL_MASTER_IMPORT` form draft. Files remain private; sheet/page/row evidence, mappings, errors, exclusions and results are persisted. Maximum 500 candidates across four files (10 MB each); PDFs retain the five-page limit. No silent truncation or Google Sheets URL access.

The model only proposes. A separate ordinary start operation verifies the stored proposal and queues analysis durably. Material-intent attachments bypass eager chat extraction. Worker jobs use 20-row/32k-character steps, 45-second budgets, 120-second fenced leases and three transient attempts (30s/2m retry). Startup and one-minute internal scheduler recovery continue analysis after the browser closes. Worker checkpoints never extend the 30-day draft lifetime.

Editable review uses expected revisions and stable row IDs. Bulk common-field corrections and select-all/clear-selection preserve source-review flags; only explicit row review acknowledges ambiguous extraction. Correction lookup returns bounded pages rather than the entire source document. Each explicit subset save uses its own idempotency token/receipt; the original card stays editable for remaining rows. Selected rows, zero-stock inventory defaults, per-material audits, readiness and receipt commit atomically. Catalog tenant locking covers AI/manual creates and identity edits. Existing/inactive name/code conflicts block creation; records are never overwritten.

New category/location/vendor proposals have separate approval and domain permissions. Vendor phone is required; Purchasing can explicitly save without vendor. A new location initializes zero inventory for all active materials. Separately approved references survive later material cancellation. Uncertain OCR must be reviewed before saving. Quantities never silently initialize stock or cash.

Apply migrations 0044/0045 before enabling the feature; deploy the scheduler with its new one-minute trigger and the existing worker secret. The internal analysis endpoint has no public web forwarding route.

## Principle

Company budget policy comes from active Budget Settings, not model knowledge, old assistant messages or a sample project's budget. Authorized chat requests receive a fresh typed policy snapshot; `getCompanyBudgetDefaults` can re-read it with `view:settings`, matching ordinary Settings read access. Missing/incomplete/failing reads are explicit non-policy states. Manual creation and AI proposals share the read-only allocation resolver, including enabled/active categories and ordering. AI budget proposals omit a fixed cap: the current configured cap/category shares apply, with a user-requested cap override still reviewed before confirmation. General questions use “perusahaan ini”; named identity comes from the active tenant.

AI is read-only by default. It may analyze, summarize, classify, and propose actions, but it must not mutate important finance or material-control data without explicit user approval through protected Server Actions.

## Agents

### Chat Agent (implemented)

Reachable from the chat button in the app header; there is no AI entry point on the Dashboard.

- Model: `stealth/ox-alpha` via OpenRouter primary **while the preview stays free ($0/$0)**, then `deepseek-v4-flash`, then `gemini-3.7-flash`. Removing `OPENROUTER_API_KEY` from the environment skips OpenRouter entirely; 401/402/429/5xx from it fall back at runtime. Fallback is decided **before the first token** only; a mid-stream failure surfaces as a retryable error instead of splicing two streams (`lib/ai/chat-stream.ts`).
- Transport: `app/api/ai/chat/route.ts`, the one internal API route, opened because `useChat` needs HTTP streaming. Read-only.
- Tools live in `lib/ai/tools/`. Every tool is read-only; `lib/ai/tools/read-only.test.ts` fails the suite if one ever writes.
- Session identity and role are closed over from the verified session — the model never supplies a user id or role. Any `projectId` the model provides is re-checked with `canAccessProject` before a query runs.
- Access requires the `use:ai_chat` permission (Owner, Finance Admin, Project Manager). The header button is hidden for roles without it.
- Conversations persist in `ai_conversation` / `ai_message`; history is always re-read server-side, never trusted from the request payload.
- Agent steps are capped at 8. DeepSeek V4 Flash calls tools far more often than Gemini, so the cap and a provider-specific system prompt keep latency and cost sane on mobile.

#### Tools

Every tool is gated by the same `PermissionKey` the rest of the app enforces, then scoped again per project for roles without global scope.

| Tool                   | Permission                 | Scope                                                                      |
| ---------------------- | -------------------------- | -------------------------------------------------------------------------- |
| `listProjects`         | —                          | Own projects unless global scope                                           |
| `getProjectBudget`     | —                          | Re-checks project access                                                   |
| `getProjectHealth`     | —                          | Re-checks project access                                                   |
| `getBankBalances`      | `view:bank_account`        | Global only (Owner, Finance Admin)                                         |
| `getPendingApprovals`  | `view:cost` + global scope | Global only — an approver's queue, never a PM's window into other projects |
| `getUpcomingBills`     | `view:vendor_bill`         | Restricted to accessible projects inside the query                         |
| `getMaterialShortage`  | `view:material`            | Re-checks project access                                                   |
| `getRecentExpenses`    | `view:cost`                | Restricted to accessible projects inside the query                         |

| `proposeExpenseDraft`  | `create:cost`              | Re-checks project access                                                   |

A denied tool returns the refusal **as data**, so the model can explain it, rather than throwing and killing the whole answer.

#### Expense proposal (the only path to a write)

`proposeExpenseDraft` writes nothing. It resolves the project, resolves the budget category **within that project's budget**, computes the total, flags whether the amount exceeds the category's remaining budget, and returns a proposal object.

The UI renders that object as a confirmation card (`features/ai-chat/components/expense-proposal-card.tsx`). Only when a human presses the button does `app/actions/ai/confirm-expense-proposal.ts` run, and that action holds no financial logic of its own: it re-validates the shape with `lib/validations/ai-proposal.ts` and delegates to `submitFieldRequest` — the same path the manual form uses, with its own RBAC, project scoping, transaction, and audit trail.

The proposal schema deliberately accepts only the fields `submitFieldRequest` needs. Stock handling, material id, and RAP item id are **not** accepted from this path, so an AI conversation can never trigger a stock side effect. The resulting record is attributed to the confirming user, never to the assistant.

There is no auto-submit, and no `sendAutomaticallyWhen` on the client.

**Existing single-document confirmation is idempotent per card.** Each proposal card carries the AI SDK `toolCallId`, which is persisted inside `ai_message.parts` and therefore survives a reload. Confirming records a row in `ai_proposal_confirmation` keyed by that id under a UNIQUE constraint, so one card can only ever produce one document — whether the button is double-clicked, two requests race, or the conversation is reopened later. When history loads, `loadConfirmedProposals` returns the executed ids and the card renders as already sent, with no button at all.

Without this, a reloaded conversation would re-offer the confirm button on a proposal that had already been recorded, and a second expense would be created for the same request.

## Rendered tool results

Answers are not plain prose. Every data tool's output is rendered as a card in the chat surface, built from the shared `components/ui` primitives (`GroupedSurface`, `MoneyValue`, `StatusBadge`, `BudgetSplitIndicator`), so a chat answer reads in the same visual language as `/ledger`.

Three rules hold this together:

1. **One source of truth for output shape.** `lib/ai/tool-output.ts` holds Zod schemas for every tool's output and carries no `server-only` marker, so tools build their return values from it and client renderers `safeParse` it. Outputs are persisted as JSON in `ai_message.parts` and read back as `unknown`; without a shared schema the renderer would silently drift from the tool and display wrong values.
2. **Renderers degrade, never guess.** `features/ai-chat/components/tool-results/` maps tool name → component. An unregistered tool, a failed parse, or an access-denied result contributes only a trace line. Messages stored before a field existed (for example before tool outputs carried `projectId`) still render, just without the deep link.
3. **The prompt names the tools that have cards.** `TOOLS_WITH_CARDS` is consumed both by the renderer registry and by the system prompt, and a test asserts the two lists match. Telling the model abstractly that "the interface shows cards" was measured and did not work — it kept restating the whole table. Naming the tools cut a typical answer from ~620 characters of bullet list to ~280 characters of prose that leads with the judgement.

Cards are rendered outside the answer bubble at full width: nesting card padding inside bubble padding squeezes the number column until a primary money value wraps at 320px.

Tool activity uses one contextual summary with manually opened details. Read sources, proposals, input requests and follow-up suggestions have distinct semantics; a proposal is never counted as a source. Active work reports the latest actual step, then answer composition, with elapsed time after ten seconds. Failures and interruptions retain the completed-step context. Only the visible active marker loops, respecting reduced motion and document visibility.

Project discovery accepts trimmed, nonempty queries of1–100 characters and keeps the20-row cap and existing scope. A single-character query is discovery, with explicit project choice required even for one match. Tool activity derives recovery before grouping: only a later genuine result from the same read tool and identical inputs can recover an ordinary failure; different tools, targets/pages, missing results, error envelopes, permission denials, mutations and interruptions retain their failure. Historical short-query validation may recover through a verified project-choice handoff when a later scoped list supplies all selector options with the other filters preserved. That historical proof remains after completion/cancellation; it does not claim the named project was found. Raw inputs/errors never become interface copy.

The existing active-input owner and current local wizard values determine waiting state. An unanswered successful project selector shows “Pilih proyek untuk melanjutkan”; selecting a valid option moves to generic remaining-form waiting. Sent, cancelled and dismissed requests stop waiting. Active generation, unresolved failure and interruption take precedence. Recovered attempts keep neutral history and a separate count; structured error results are treated as failures even with SDK output-available and show a safe category/recovery explanation. Shared FormDisclosure/AppIcon/motion ownership and reduced-motion behavior remain unchanged.

The composer dock owns ordinary entry (attachments, growing textarea and stable Send/Stop) and the step-by-step input wizard. Wizard values/current/furthest step live above animated content swaps. Pause/resume retains normal draft and wizard values; typed shared controls use embedded grouped presentation and shared select/calendar overlays. An unanswered request survives unrelated replies; formatted submission or explicit cancellation prevents resurrection from persisted history. Answering the wizard sends a chat reply and preserves unrelated unsent text/attachments; it does not approve business writes. Automatic scrolling follows the answer only until the latest user message reaches the top reading inset. Upward reading gestures pause following. Opening a conversation and explicitly pressing “Ke jawaban terbaru” may go to the actual bottom; a new send restores the question limit. Composer growth never pulls the reader backwards. Shared AppIcon provides real Stop and interrupted-state glyphs.

Wizard Next always advances one visible primary step, including after revisiting a filled chip. Typed `visibleWhen` and `groupWith` fields form conditional inline groups; selecting a new client reveals its required name within the client step. Legacy stored “+ Klien Baru (tulis di bawah)” requests normalize to that branch. Hidden branch values stay available for switching back but are omitted from the chat submission. A new-client choice is a presentation sentinel, never a database client ID. Desktop AI chat shares the mobile gray canvas and composer tones, with a centered 664px conversation lane, assistant content/cards up to 600px and user bubbles/attachments up to 480px. The composer container remains up to 704px including side clearance, aligning its visible 664px surface with the conversation lane. Short bubbles remain intrinsic; shared proposal/result shells stay width-neutral and detailed review portals retain their wide presentation. Native surface=mobile uses the original mobile composition. Focused controls and active pointer presses retain their presenter through resize until the ensuing click completes.

New-project requests use the optional `CREATE_PROJECT` workflow hint; legacy forms are recognized from their project-name field and creation title. Their cap, margin and allocation-ratio fields are removed during normalization, including persisted requests, so stale local values never enter the submission. Project proposals read the active Settings snapshot and show a compact cap/margin summary with disclosed category amounts. Creation already inserts the initial canonical budget: it does not require a second setup proposal. Confirmation compares reviewed Settings with one fresh transaction snapshot and uses that same snapshot to write; changed settings require a new proposal. Legacy proposals and manual creation keep their existing default behavior. Unsupported special caps are never smuggled into project notes; explicit setup-budget overrides remain in their existing workflow.

`suggestFollowUps` is a read-only tool that only validates and de-duplicates the model's own suggestions, returning them as structured data so the interface can render real buttons. It runs as the last step, which is why `stopWhen` is 10 rather than 8.

Desktop AI uses a permission-gated sidebar entry, active conversation title and labelled New/History controls. One persistent history owner forms an adaptive rail; mobile uses the existing full history view. Composer wizard state is controlled by the workspace and persists alongside text, attachment references and dismissed requests in a versioned user-scoped session cache (up to 20 drafts). The last opened owned chat restores on entry; local unsent drafts are separate from backend conversations. Switching awaits stream stop, ignores outdated fetch results and clears outgoing input before restoring the target. History errors/no-results are distinct. Welcome actions come from the same server-side capability catalogue through a read-only typed facade, including actual permissions and project scope. Shared rename/delete/preferences dialogs retain their ownership across resize. Business writes still require their existing explicit confirmation.

## Conversations

Conversations are listed, switched, and deleted from inside the chat sheet (`features/ai-chat/components/conversation-picker.tsx`). "Mulai percakapan baru" creates an empty conversation server-side first, so its id is available to a proposal card from the very first message; the title is filled from that first message by `setConversationTitleIfEmpty`, which is safe to call repeatedly because it only writes when the title is still null.

Deleting a conversation removes its messages and confirmation records. It deliberately does **not** remove documents that were already created from its proposal cards — a recorded expense is a financial record, correctable only through the proper reversal path.

## Data AI May Read

- Project budget and actual cost aggregates.
- Settings-backed expense categories and Budget Allocation defaults.
- Category budget cards: Tukang, Material, Operasional, Lain-lain, and Subcon budget/actual/remaining/used/status.
- Item & Price Library references for draft suggestions only.
- RAP item status and shortage calculations.
- Inventory availability, reserved stock, and leftover/reusable stock.
- Vendor bills due and recent project expenses.
- Historical `ai_run` summaries.

## Data AI Must Not Expose

- Internal RAP cost, margin, markup, vendor notes, or internal notes in client-facing RAB output.
- Global cash/ledger data to users without permission.
- Other PM projects to scoped project users.

## Mutation Rule

AI output can power proposal cards or prefilled forms. Final writes must be triggered by a human action and routed through Zod-validated, RBAC-protected Server Actions.

This is enforced mechanically, not just by convention. `lib/ai/tools/read-only.test.ts` fails the suite when any file under `lib/ai/tools/` contains `db.insert`, `db.update`, `db.delete`, `db.execute`, a transaction, or an import from `@/app/actions/**`. Adding a write-capable tool requires deleting that test, which is the point.

## Prompt Injection

Names, notes, and descriptions returned by tools are text other users typed. The system prompt states explicitly that tool output is data and never an instruction. Because every tool is read-only, the worst case for a successful injection is a misleading answer, not a mutation — which is the main reason the read-only rule is enforced by test rather than left to review.

## Output Language

Owner-facing summaries should be practical, short, and written in simple Bahasa Indonesia.
