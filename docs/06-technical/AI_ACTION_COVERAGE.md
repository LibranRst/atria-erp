# AI action coverage

[Role/permission acceptance](../guide/ai-role-permission-verification-2026-10-13.md) exercises the four canonical roles, declared custom scopes, foreign-owned proof and live revocation. Legacy reads now retain instance boundaries; stock-bearing catalog lookup additionally requires inventory-read access. Denied /ai entry uses a server permission gate and the shared restricted state, not a composer that will fail later. These sampled checks do not certify every action or permission subset.

[Operational live acceptance](../guide/ai-operational-live-verification-2026-10-13.md) completes one synthetic project through RAP/RAB approval, activation, linked vendor bill/receipt, reservation/use, payment and bank reconciliation with explicit UI confirmations. Exact budget/cash/stock checks, request replays and history/reload remain consistent. Gateway object-union hints retain original validation, default selling prices use stored precision, and bank result rows retain unique identity. CSV import used reviewed chat contents; private attachment storage was unavailable on that QA API.

Updated 2026-10-13. Runtime authority is `lib/ai/tools/capability-catalog.ts`: effective database grants and project scope select tools. Tool-name/role-name constants never grant rights. A capability is available only where the user's effective permissions permit it; confirmation independently validates permission and live data.

Factual expense replies now use current scoped `getRecentExpenses` reads with stable canonical IDs, separate field-expense IDs, exact amounts, current workflow/payment status, source type, requested dates and explicit pagination. Duplicate descriptions require selection; a recent page is not a project total. `getFinancialHistory` calculates full scoped recorded-expense and cash-flow aggregates for one or two supported periods, derived from the original human question in Asia/Jakarta. Recognized costs, inventory purchases and cash movement remain separate; opening balances, internal transfers and adjustments are disclosed as cash-flow exclusions. Current source reads and exact server calculations replace model-written amounts before publication and persistence. Past balance/budget/stock/approval snapshots and forecasts remain explicitly unavailable; present values never substitute for them. See the [factual coverage verification](../guide/ai-factual-finish-verification-2026-10-13.md) for tested scope and limitations.

[Live acceptance](../guide/ai-live-conversation-verification-2026-10-13.md) qualifies sampled stock/profile writes, Settings lookup, completed setup and a denied project path with the configured NINEROUTER model, not this whole inventory. Regular creation requires create:project and create:budget with global scope; its wizard and capability explanation use that gate rather than treating a missing tool as unimplemented.

Staff/role administration now covers partial staff name/role/activity changes (including atomic batches), role metadata/project-scope corrections and unused custom-role deletion through the immutable ADMINISTRATION family. Actual company membership and management grants are checked after locking; Owner/system/self/escalation/sensitive-assignment and last-active-critical-holder guards remain. Changes synchronize membership and revoke affected sessions without rewriting passwords, assignments or business history. Referenced roles, including inactive holders, cannot be deleted. Creation and governed permission proposals remain separate; credential and protected Owner changes retain Settings.

`getCompanyBudgetDefaults` supports read-only company policy lookup through `view:settings`, using active Budget Settings and the shared manual allocation resolver. Authorized chat requests also receive current policy context. AI setup proposals use configured cap/category shares and explicit reviewed overrides; Company cap/category default changes use getBudgetSettingsContext/proposeBudgetSettings with actual company Settings rights, a complete before/after review and protected identity-only confirmation; existing project budgets remain unchanged.

Operational Settings use getOperationalSettingsContext/getExpenseCategorySettingsContext with view:settings, then proposeApprovalThresholds/proposeExpenseCategorySettings and the existing identity-only Finance Input confirmer. Mutations require actual approval/category management rights, and ratio corrections additionally require budget management. Threshold policy applies to later evaluations, not pending submissions; category corrections preserve canonical codes and existing monetary records. Shared transactional writers serve manual and AI changes.

This inventory covers every explicitly registered web action, including compatibility/read adapters. “Supported” means the named chat proposal/confirmation route exists; it does not imply unrestricted execution. Material creation remains create-only. Existing Material Master metadata/status changes use proposeUpdateMaterial with a stored server snapshot and explicit confirmation. RAP Material creation/append use proposeRapMaterialDraft with budget-first review and identity-only confirmation. RAP readiness/Ready/scope/stage/finalization uses getRapSetupContext and proposeRapSetupActions with explicit ordered decisions and identity-only confirmation. Tukang/Subcon Draft package creation/editing uses getCategoryPlanContext and proposeCategoryPlanPackages with per-category budget review and identity-only batch confirmation. Saved latest-Draft item edits/deletions use getEditableRapItems and proposeRapMaterialChanges, immutable before/after snapshots and atomic identity-only confirmation. Remaining RAP lifecycle uses getRapLifecycleContext/proposeRapLifecycleActions for revisions, Edit Lagi/deletion of packages, and manual/library Material additions. Client RAB draft generation uses getRabDraftContext/proposeRabDraft with eligible latest sources, server-derived selling defaults, owned review corrections/selection and identity/revision-only atomic confirmation. It creates exactly the selected reviewed rows; existing approved baselines remain intact, while baseline manual rows/bundles are not copied implicitly. Saved RAB corrections, manual additions, exclusion/restoration, bundles, initial approval, baseline revision/cancellation and Change Order creation/client attestation/approval/rejection use getRabWorkflowContext/proposeRabWorkflow with immutable before/after review and identity-only transactional confirmation. Approval previews contract/cap/category effects only with budget-read access. Client attestation requires human-supplied date/reference; Change Order approval retains maker/checker and explicit emergency rules. Project stock reserve/release/use/return/waste now uses getProjectStockContext/proposeProjectStock with exact before/after, source attribution and identity-only atomic confirmation. Existing warehouse NONE access through create:stock_movement remains domain-only; ASSIGNED remains restricted. USE/RETURN/WASTE may affect noncash Material actuals; RESERVE/RELEASE_RESERVATION do not. Receipt reversal request/independent approval/rejection uses getWarehouseContext/proposeWarehouseOperation with complete-receipt stock/value/reservation guards, scope checks and no AI emergency self-approval. Vendor invoice drafting/submission now uses getVendorBillContext/proposeVendorBill and ordinary owned VENDOR_BILL_CREATE drafts, separately from payment. Warehouse transfers and stock-count draft/submission/independent approval/rejection use getWarehouseContext/proposeWarehouseOperation. Both use identity-only transactional confirmation, live rights and exact source snapshots. Vendor create/edit/status, item-library create/edit/archive/status, pricing-template/component replacement, inventory defaults and separate valuation now use getCatalogSettingsContext/proposeCatalogSettings with current tenant sources and exact immutable review. Linked Draft RAB source refresh now uses proposeRabWorkflow REFRESH_SOURCES and the shared manual writer; its public preview retains client labels, descriptions, visibility and bundle prices. Client invoice/schedule creation uses getClientInvoiceContext/proposeClientInvoice; shared transactional writers create unpaid invoices without cash movements. Company budget defaults use getBudgetSettingsContext/proposeBudgetSettings and the shared Settings writer. Bank account creation/metadata/status and company cash/transfer now use getBankCashContext/proposeBankCash with shared manual/AI writers, sorted account locks, reviewed balances/references and identity-only receipt-backed confirmation. This records Atria cash, not an external bank transfer. RAB export now uses getRabExportContext/prepareRabExport with owned source-checked client-safe PDF/Excel/PNG downloads; local document appearance remains human-controlled in the shared workbench. Emergency adjustments, credentials and protected security configuration retain ordinary forms. Own-profile and Quick Start changes use their explicit supported chat workflows. Owner-user creation and sensitive role grants retain their manual restrictions.

Capability answers distinguish permission-filtered read tools, proposal tools requiring a user button, and implemented ERP workflows that remain manual. explainUserAccess is authorization context, not the AI action inventory.

Analysis jobs and draft edits write only AI metadata. Business records change only through the corresponding explicit human confirmation operation. Purchasing gets chat access; vendor creation still requires `manage:vendors`. Native uses the existing web chat fallback.

Review depth follows the deterministic web presentation policy: small changes expose complete differences and an action on the chat card; sensitive decisions add one short confirmation; complex lists, edits, selections and imports retain dedicated review. This changes interaction depth, not action coverage, permission, proof or transactional authority.

Coverage is per **business behavior**, not a count of transport functions. `Partial support` names the supported subset and the remaining restriction. `Legacy/manual` preserves compatibility flows without advertising the legacy model as another chat workflow. `Infrastructure/manual` covers uploads, notifications, authentication/simulation, local draft storage and onboarding progression; these are not executable AI business gaps. Actual business gaps remain `Gap`. The inventory consistency test checks every fixed registered operation, unique rows, registered proposal-tool references and callable confirmation names.

New invoice examples: “Siapkan invoice DP Rp20 juta untuk [proyek], nomor INV-001, jatuh tempo 30 Oktober 2026”; “Buat jadwal DP30%, progres40%, pelunasan30%, mulai 31 Oktober 2026.” Dates and amounts are explicit, monthly dates clamp to the month's last day and the final installment absorbs the cent remainder. Schedules reject existing active invoices. The user can correct through chat and must press the proposal's save button.

Default example: “Ubah plafon default perusahaan menjadi85%, pertahankan porsi kategori lain.” AI reads the full active setting, preserves untouched categories and previews derived margin. The change updates company defaults, requires `manage:budget_settings` plus Settings read rights, and does not recalculate existing projects or change approval thresholds.
