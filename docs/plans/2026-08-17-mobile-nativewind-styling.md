# Mobile styling: NativeWind adoption

**Status:** infra live, pilot screen (Ledger Ringkasan tab) converted and visually verified in the iOS Simulator against real data. Rest of the app not yet converted.

## Why

Audit of the native shell against the web dashboard (see `docs/plans/2026-08-15-expo-migration-handoff.md`, "Audit · Fidelity Dashboard vs web") found section/content styling drifting from web across ledger tabs. Root cause: `apps/mobile` styles everything with `StyleSheet.create` + hand-authored `theme.ts` values, so every screen re-derives spacing/type/color decisions instead of reusing the same utility vocabulary the web app writes against `apps/web/app/globals.css`. User direction (2026-08-17): style with NativeWind so mobile can be authored in Tailwind classes, explicitly **not** required to byte-match Tailwind v4 syntax — use NativeWind's current stable release and adapt.

Scope boundary carried over from the prior audit and still in force: sheet/modal/tab-bar chrome stays native-raw (iOS liquid glass on iOS, iOS-styled — not Material — on Android). This work is about section/page **content** styling only.

## Version decision

- `nativewind@4.2.6` (latest stable) + `tailwindcss@3.4.19`, not the `5.0.0-preview.*` line. NativeWind v5 targets Tailwind v4's CSS-first engine and is still preview-only (confirmed via `npm view nativewind versions`); v4.2.6 is the last stable release, uses a `tailwind.config.js`-style (Tailwind v3) config, and is what Expo/RN projects use in production today. This is the "current version, not 4.0" the user asked for — current means current _stable NativeWind_, not an attempt to replicate the web's Tailwind v4 CSS-first config on native.

## Token pipeline

`apps/mobile/tailwind.config.js` is **generated**, not hand-authored — mirrors the existing pattern where `packages/tokens/src/tokens.ts` is generated from `apps/web/app/globals.css`.

- New generator: `scripts/generate-mobile-tailwind-config.ts`, run via `bun run mobile-tailwind:generate`.
- Reads `colors`, `spacing`, `radii`, `maxWidths`, `typography`, `opacityColors` from `packages/tokens/src/tokens.ts` and writes `apps/mobile/tailwind.config.js` with kebab-case keys matching the web's actual generated class names 1:1 (e.g. `bg-on-surface-variant`, `p-md`, `rounded-owner`, `text-section`) — so a class typed on native reads the same as its web counterpart.
- Font family scale (`font-sans`, `font-sans-medium` … `font-sans-bold`, `font-mono`) is hardcoded in the generator to the Expo Google Fonts weighted family names (`Manrope_700Bold`, etc.) since those names are mobile-specific (tied to `@expo-google-fonts/*` packages) and don't exist in the shared token source.
- **Not mapped as a generated utility:** `shadows`. Web's shadow tokens are multi-layer CSS `box-shadow` strings including inset layers, expressed as plain CSS strings. React Native's Fabric renderer (this project's RN 0.86.2) _does_ accept a CSS-syntax `boxShadow` string directly on `style`, so these keep working — they're just applied via `style={{ boxShadow: theme.shadows.x }}` alongside `className`, not as a generated Tailwind class (NativeWind's own arbitrary-value shadow utilities are a much worse fit for a multi-layer string than just passing it straight through).
- Whenever `packages/tokens/src/tokens.ts` regenerates (i.e. `bun run tokens:generate` after a `globals.css` change), re-run `bun run mobile-tailwind:generate` to keep the two in sync.

## Infra changes (done)

- `apps/mobile/babel.config.js` — `babel-preset-expo` + `nativewind/babel`.
- `apps/mobile/metro.config.js` — wrapped with `withNativeWind({ input: "./src/global.css" })`, plus a custom `resolver.resolveRequest` (see "The real bug" below).
- `apps/mobile/src/global.css` — the three `@tailwind` directives.
- `apps/mobile/src/app/_layout.tsx` — imports `@/global.css` first.
- `apps/mobile/nativewind-env.d.ts` + `apps/mobile/tsconfig.json` `include` — auto-generated by NativeWind's Metro plugin on first run; do not hand-edit, do not remove from `include`.
- Added devDependency `babel-preset-expo` directly to `apps/mobile` (Expo's Metro babel transformer resolves it implicitly when no `babel.config.js` exists, but a custom config must declare it explicitly to be resolvable).
- `apps/mobile/app.json` — `ios.infoPlist.NSAppTransportSecurity.NSAllowsArbitraryLoads: true`. Needed so the debug client can call the local dev API over plain HTTP on a LAN IP (`EXPO_PUBLIC_API_URL`). Debug-build-only convenience; production builds should use HTTPS instead of loosening this further.
- `apps/mobile/.env` (gitignored) — `EXPO_PUBLIC_API_URL=http://192.168.1.21:3000` for this dev machine so the login flow's session check can reach the local web server from the simulator. `localhost` also works for the _simulator_ specifically (it shares the host's network namespace) but the LAN IP is what a real device needs, so that's what's recorded here as the working value.
- Root `bunfig.toml` (new file) — `[install] linker = "hoisted"`. Monorepo-wide blast radius, flagged deliberately. See "Bun linker" below.

## The real bug: two physical copies of `react-native-css-interop`

This is the one that actually mattered and cost the most time. Everything above made the build _compile_; this is why classes compiled but had **zero visual effect** — `<View className="bg-surface-inverse ..." />` rendered as if `className` were a no-op (no color, no radius, no reserved size for `h-`/`w-` utilities either).

**Diagnosis path:** fetching the live Metro bundle via `curl http://localhost:8081/.expo/.virtual-metro-entry.bundle` and grepping it directly (rather than guessing) showed the compiled Tailwind stylesheet registry _did_ have correct rules (`"bg-surface-inverse":{...backgroundColor:"#181817"}`), and the JSX in `ledger/index.tsx` _did_ compile through `_reactNativeCssInteropJsxRuntime.jsx` as expected. Both halves looked right individually. Tracing the Metro module-path suffix on each `__d(...)` registration showed why they never talked to each other: the file that calls `injectData(...)` (nativewind's generated `.cache/ios.js`) required `react-native-css-interop/dist/runtime/native/styles` and got the copy living at `node_modules/.bun/react-native-css-interop@0.2.6+fc4d0fa6e32f52be/...`, while `ledger/index.tsx`'s compiled JSX runtime import resolved `react-native-css-interop/jsx-runtime` to a _different_ physical copy at the repo-root `node_modules/react-native-css-interop`. Two separate module instances of the same package means two separate copies of whatever internal registry `injectData` writes into — styles got registered in one, read from the other, always empty.

**Root cause:** `react-native-css-interop` declares `peerDependencies: { tailwindcss: "~3" }`. This monorepo has two different `tailwindcss` majors present — `apps/web` runs real Tailwind v4 (`^4.3.3`) for its own CSS, `apps/mobile` has `tailwindcss@3.4.19` as a NativeWind devDependency. Bun's installer resolves/hashes a package's on-disk location partly by its peer context, so it materialized two distinct copies of `react-native-css-interop` rather than one — and `linker = "hoisted"` (added earlier for the Babel plugin-resolution problem) doesn't prevent this, since it's a genuine peer-driven split, not a missing-hoist bug.

**Fix:** `apps/mobile/metro.config.js` now installs a custom `resolver.resolveRequest` that intercepts every `"react-native-css-interop"` / `"react-native-css-interop/*"` request — from _any_ file, including ones already living inside the other copy — and redirects it to one canonical path (`../../node_modules/react-native-css-interop`, the repo-root copy). `resolver.extraNodeModules` was tried first and does **not** work for this: it's only a fallback consulted when normal resolution _fails_, and normal resolution here always succeeds (it just succeeds twice, at two different paths), so it never even got a chance to run. `resolveRequest` runs unconditionally for every module request and was necessary.

Verified via the same bundle-grep technique: after the fix, every `react-native-css-interop` file in the bundle — including the injected-styles module and the jsx-runtime's own internal chain — resolves to the identical Metro module ID. Confirmed visually immediately after: the dark position card, the three translucent metric boxes, and the budget progress box all render with correct background colors, radii, and text colors on first load.

## Other build-environment bugs found and fixed along the way

None of these are NativeWind-specific — they're pre-existing gaps in this project's ability to do a **from-scratch local `expo run:ios`**, surfaced only because this session was the first time that path got exercised end-to-end since the repo moved to (or has always been at) a path containing a space: `/Volumes/DekoriaSSD/App Projects/Websites/atria-erp`.

- **CocoaPods `pod install` failure with a non-UTF-8 shell locale.** Fixed by running with `LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8` (CocoaPods itself printed this exact remediation).
- **Two separate unquoted-`$PROJECT_DIR`-style bugs in generated Xcode build-phase scripts**, both only surfacing because the path contains a space:
  - `Pods.xcodeproj`'s `[CP-User] Generate app.config for prebuilt Constants.manifest` phase ran `bash -l -c "$PODS_TARGET_SRCROOT/../scripts/get-app-config-ios.sh"` — the _outer_ shell's word-splitting turned the space-containing path into multiple arguments to `bash -c`, which then tried to execute `/Volumes/DekoriaSSD/App` as a command. Same bug pattern in `AtriaERP.xcodeproj`'s "Bundle React Native code and images" phase, which back-tick-substitutes a Node-computed path and executes it unquoted. Both required editing the generated `.pbxproj` directly (ephemeral — `ios/` is gitignored and regenerated by `expo prebuild`, so this isn't a committed fix, just something to redo if `ios/` gets wiped and rebuilt from scratch again).
  - The real, _persistent_ one: `node_modules/expo-constants/scripts/get-app-config-ios.sh` itself has `PROJECT_DIR_BASENAME=$(basename $PROJECT_DIR)` — unquoted, so on this path it silently resolved to `"App"` instead of `"Pods"`, failed the script's own `if [ "x$PROJECT_DIR_BASENAME" != "xPods" ]` guard, and the script no-op'd on every single build without ever erroring. This is what caused the `expo-linking needs access to the expo-constants manifest` crash on _every_ app launch, unrelated to login or networking — traced by manually running the script with `bash -x` and matching env vars until the silent early-exit was visible. Fixed by quoting: `basename "$PROJECT_DIR"`. This lives in `node_modules` (not committed) — a fresh `bun install` restores the buggy version. If this bites again, the fix is one word (add quotes around `$PROJECT_DIR` on that line).

None of the four are things this project should try to permanently patch via `node_modules` edits (they'd be silently lost on every `bun install`). They're recorded here as a runbook for whoever hits `expo run:ios` cold on this machine next, not as done infrastructure work — the actual persistent, committed fixes are the `bunfig.toml` linker setting and the `metro.config.js` resolver above.

## Bun linker (`bunfig.toml`)

`[install] linker = "hoisted"`. Bun's default install layout for this workspace is an isolated, pnpm-style store (`node_modules/.bun/<pkg>@version/node_modules/...`) with each workspace package's own `node_modules/` symlinking only its _direct_ dependencies. Metro's Babel worker runs under plain Node and resolves plugins with classic `require()` semantics, walking up the directory tree — it cannot see into Bun's isolated store for a preset's _transitive_ plugins (e.g. `babel-preset-expo` → `@babel/plugin-transform-react-jsx` failed with `MODULE_NOT_FOUND` before this change, even though the package existed in the store). `linker = "hoisted"` makes Bun flatten `node_modules` like npm/yarn classic, which Metro needs. This should be neutral-to-positive for `apps/web` (flat node_modules is the more universally-compatible layout, not a stricter one) — confirmed via full `bun run lint` and `bun run test` across all four workspaces, all clean, after the switch.
