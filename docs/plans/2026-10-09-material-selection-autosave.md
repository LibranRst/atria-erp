# Responsive Material draft selection

Current Material selection calls the general blocking operation runner for every click. It waits for the server response before updating the checkmark and disables every row, page and footer action during that wait. Selection changes are draft metadata, so the interaction should respond immediately while preserving the acknowledged revision required for business Save.

Keep the existing shared ChoiceRow, review rows and backend selection operation. Project the latest local selection into the existing draft immediately; serialize autosaves and coalesce intermediate choices so earlier responses cannot replace later clicks. Use the last acknowledged server revision for each write. Separate selection synchronization from business operation pending state; checkbox, select-all/clear, pagination and filters remain usable while synchronization runs. Business Save, field corrections, references and discard cannot race an unacknowledged selection.

On failure retain the visible unsaved choices, provide an explicit retry and block business Save. Retry first reads the latest owned draft, then applies only selection metadata for the remaining rows. Closing/reopening review or responsive resize must preserve the latest choices. No optimistic business creation or permission bypass.

Regression uses the actual Material component with delayed server responses: immediate checkmark, another enabled checkbox, serialized current-revision writes, stale-response protection, Save barrier and failure/retry retention. Verify through the dev in-app Browser, existing Material/RAB review tests, web/API/mobile types, workspace lint/format and web build. Refresh documentation and Graft.
